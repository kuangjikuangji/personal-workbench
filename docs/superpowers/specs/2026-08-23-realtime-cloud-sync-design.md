# 个人工作学习工作台业务数据云端化与实时同步设计

## 目标

将工作台全部业务数据从仅存于浏览器的 IndexedDB 升级为由 Supabase PostgreSQL 持久化、Supabase Realtime 分发变化、IndexedDB 提供离线镜像的本地优先系统。同一账号在不同终端登录后必须看到相同数据；断网期间仍可新增、修改和删除，恢复联网后自动同步。

## 范围

本次覆盖现有全部业务实体：待办、学期、课程、教师、教师年度汇总、教师记录、指导关系、研究资料、学习方法、灵感、教案、学生、学生记录和应用设置。

当前工作台没有已录入业务数据，因此不提供旧 IndexedDB 数据导入流程。主题、提醒去重记录和 PWA 安装状态等纯终端偏好继续保存在本地；它们不属于跨终端业务数据。

## 核心架构

系统采用“Supabase 云端主库 + IndexedDB 离线镜像 + 本地待同步操作队列”。界面始终从 IndexedDB 镜像读取，并先写本地，因此在线和离线操作具有一致的即时响应。后台同步引擎在登录且网络可用时，将本地操作队列按顺序提交到 Supabase；同时订阅 Supabase Realtime，将其他终端产生的变化写回镜像并刷新 React Query。

Supabase 是最终持久化来源，IndexedDB 不是独立数据孤岛。首次登录或本地镜像需要重建时，客户端执行一次完整云端拉取；之后通过本地操作队列和实时事件保持增量一致。

## 云端数据模型

为每类业务实体建立独立 PostgreSQL 表，沿用现有 TypeScript 实体字段，数据库列使用 snake_case。所有实体表包含：

- `id uuid`：客户端生成的稳定主键。
- `user_id uuid not null`：引用 `auth.users(id)`，标识数据所有者。
- `created_at timestamptz not null`：创建时间。
- `updated_at timestamptz not null`：最后修改时间，用于最后修改者优先。
- `deleted_at timestamptz null`：软删除时间；非空记录不出现在正常查询中。

业务关系保留现有 ID 引用，并在同一用户范围内建立必要索引。数组字段使用 PostgreSQL 数组，`week_rule` 和设置值使用 `jsonb`。数据库触发器校验 `updated_at`，并保证同一用户下教师年度汇总的 `(teacher_id, year)` 唯一性。

所有业务表加入 Supabase Realtime publication。实时事件必须包含足够的旧记录身份信息，以便客户端处理删除和所有者过滤。

## 权限与安全

所有业务表启用 Row Level Security。`select`、`insert`、`update` 和 `delete` 策略均要求 `auth.uid() = user_id`，客户端不得替其他用户写入数据。外键关联记录还需通过约束或触发器验证属于同一用户，避免跨用户引用。

浏览器仅使用公开的 Supabase URL 和 anon/publishable key；service role key 只用于受控的部署或管理脚本，不进入前端构建、GitHub 仓库或浏览器存储。

退出登录时关闭 Realtime channel、停止同步任务、清除本地业务镜像和待同步队列，确保同一设备上的下一位用户无法看到前一账号的缓存。

## 本地镜像与操作队列

现有 Dexie 业务表继续作为 UI 查询镜像，并升级数据库版本，新增：

- `syncOperations`：保存操作 ID、用户 ID、实体类型、实体 ID、操作类型、完整数据快照、客户端修改时间、重试次数、最后错误和创建时间。
- `syncMetadata`：保存当前镜像所属用户、最近一次完整拉取时间和同步协议版本。

业务仓库接口保持不变，避免功能页面感知存储层改造。仓库的新增、修改、覆盖和删除在同一个 Dexie 事务内同时更新镜像并写入同步操作。连续操作在上传前可按实体合并：多次更新保留最后快照；新增后更新合并为一次 upsert；新增后删除可直接抵消；已同步记录的删除写入墓碑操作。

删除在本地立即从正常查询中消失，但云端使用 `deleted_at` 保留墓碑，以便离线终端恢复后能获知删除事件。

## 同步流程

登录并完成强制改密后，同步会话按以下顺序启动：

1. 绑定当前 Supabase 用户；若本地镜像属于其他用户或协议版本不兼容，先清空业务镜像。
2. 建立 Realtime 订阅，并记录订阅就绪状态。
3. 完整拉取当前用户全部未删除记录及必要墓碑，写入 IndexedDB 镜像。
4. 上传本地待同步队列；每项成功后删除队列记录，临时失败则保留并退避重试。
5. 进入稳定状态，实时事件持续合并到镜像；浏览器恢复在线、窗口重新聚焦或 Realtime 重连时再次执行增量核对和队列冲刷。

为避免订阅建立和初始拉取之间丢失变化，订阅先于拉取建立；实时事件和拉取结果均通过同一幂等合并函数处理。

## 冲突规则

冲突采用已确认的“最后修改者优先”：比较客户端记录的 `updated_at`，时间较新的完整记录胜出。删除被视为带 `deleted_at` 的版本；删除时间晚于对方修改时间时删除胜出，早于对方修改时间时较新的修改可恢复记录。

客户端时间可能有偏差，因此服务端接受提交时返回数据库时间并更新本地镜像。系统为个人工作台设计，不增加人工冲突解决界面。所有 upsert 和事件合并必须幂等，相同操作重复提交不得产生重复记录。

## 网络、失败与恢复

同步引擎区分以下状态：

- `synced`：队列为空且已连接实时通道。
- `syncing`：正在拉取、上传或应用远端变化。
- `offline`：浏览器离线；界面继续允许本地写入，并显示待同步数量。
- `error`：联网但同步失败；显示简短错误和手动重试入口，队列不得丢失。

临时网络错误、超时和服务不可用采用有上限的指数退避；鉴权失效停止写入并返回登录流程；权限或数据校验错误保留失败操作并显示可操作提示。刷新页面或关闭浏览器后，未同步队列仍保存在 IndexedDB，下一次登录同一用户后继续。

## 界面变化

应用外壳显示紧凑的同步状态：已同步、正在同步、离线且有若干项待同步、同步失败。错误状态提供“重试”按钮。业务表单和列表保持现有交互；本地事务成功即视为保存成功，不等待云端响应。

首次云端加载期间显示明确的加载状态，完成后再呈现业务页面，避免短暂显示空数据。Realtime 事件应用后，通过统一查询失效机制刷新受影响页面。

## 测试与验收

数据库测试必须验证：所有表存在、RLS 阻止跨用户读写、同一用户可正常 CRUD、关联数据不能跨用户引用、软删除和冲突函数符合规则、所有业务表已启用 Realtime。

前端单元测试必须覆盖：本地写入与入队的原子性、队列压缩、成功确认、失败重试、最后修改者优先、删除墓碑、用户切换清缓存、实时事件合并和同步状态转换。

端到端测试使用两个独立浏览器上下文登录同一账号，验证终端 A 新增、修改和删除后终端 B 自动更新；验证终端 A 断网修改、刷新页面后数据仍存在，恢复联网后终端 B 收到变化；验证退出登录后本地镜像被清除。

部署验收包括 Supabase migrations 推送、Realtime publication 和 RLS 在线验证、生产构建、完整测试、GitHub 合并、Pages 发布成功及线上双终端检查。

## 不在本次范围

- 多人共享同一条数据或协作权限。
- 历史版本浏览和人工冲突解决。
- 附件或文件上传。
- 对当前空 IndexedDB 的数据迁移。
- 将主题、PWA 状态等终端偏好同步到云端。
